## Context

Репозиторий пуст: есть `plan.md` (техническое задание с примерами кода) и пустая `src/`. Мотивация изменения — в `proposal.md` (Why), требования — в `specs/{game-rules,level-loading,player-input,game-rendering}/spec.md`. Здесь только то, что определяет способ реализации.

Фиксированные входные данные:

- Инструментарий: `bun` как пакетный менеджер и раннер, dev-зависимости — `typescript`, `@biomejs/biome`, `@types/bun`, runtime-зависимостей ноль.
- Окружение исполнения: браузер, только нативные Web API (`Canvas 2D`, `requestAnimationFrame`, `fetch`, `Pointer Events`).
- Строгий TypeScript с `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`.
- Ассеты — заглушки; реальные спрайты придут отдельным изменением, контракт атласа уже зафиксирован.

Два факта, которые ломают исходный `plan.md` и требуют решений (приняты пользователем, зафиксированы ниже):

1. **Победа по исходным правилам недостижима.** Если ход разрешён только на `soil`, клетка игрока всегда `soil`, `soilCount` падает максимум `N-1` раз и никогда не доходит до `0`.
2. **Браузер не исполняет `.ts`.** `<script type="module" src="./src/index.ts">` из `plan.md` без флагов браузера не работает, поэтому «сборщик не нужен» — фактически неверно.

## Goals / Non-Goals

**Goals:**

- Правила геймплея — чистые функции над плоским мутируемым состоянием, без DOM и без колбэков: результат хода проверяется исполняемой проверкой без браузера.
- Всё, что видно глазом, проверяется без браузера: правила, раскладка и разбор ввода — чистые функции, DOM только читает события и рисует; тесты идут через `bun test`.
- Данные уровней и атласа валидируются на границе доверия: несоответствие размеров, неизвестный тип клетки, отсутствующая стартовая позиция, неизвестное имя кадра — явная ошибка, а не тихий сбой.
- Один ход на один `update`, ввод не теряется между кадрами.
- Ровно одна точечная перерисовка клетки на ход, анимация игрока — time-based и не зависит от ходов.
- Весь скелет — ноль runtime-зависимостей, три dev-зависимости, сборка одной командой.

**Non-Goals:**

- Никаких интерфейсов и DI: `Renderer`, `Game`, `InputSource` с одной реализацией не заводим — модули экспортируют функции и plain-объекты.
- Никакой браузерной автоматизации и снапшот-тестов картинки: тестируется логика и раскладка, а не пиксели (см. D10).
- Никакой анимации перемещения: кролик переносится мгновенно между клетками (так требует `game-rendering`, сценарий «Кролик перемещается вместе с позицией»).
- Никаких undo, рестарта, сохранения, меню, звука и текстовых надписей — это уже вне scope в `proposal.md`.
- Никаких дополнительных слоёв абстракции «на вырост»: если понадобится второй уровень сложности или редактор — отдельное изменение.

## Decisions

### D1. Асфальтируется клетка назначения, а не отправления

**Что:** после успешного хода клетка, НА КОТОРУЮ игрок перешёл, становится `road`, `soilCount` уменьшается на единицу; клетка, с которой ушёл, остаётся `road`.

**Почему:** единственный вариант из рассмотренных, при котором условие победы достижимо и непротиворечиво. Побочный эффект правила — игра становится настоящей логической задачей: маршрут обязан посетить каждую `soil` ровно один раз (возвращаться по своему асфальту нельзя), а неверный ход может отрезать непосещённую землю и загнать игрока в тупик.

**Альтернативы:**
- Исходное правило `plan.md` (замощается клетка, с которой ушёл, а победа — «маршрут закончился на старте») — отклонено как физически неиграбельное: уход со старта немедленно замощал его, вернуться было нельзя, поэтому вернуться и выиграть невозможно никогда.
- Стартовая клетка как `soil`, замощаемая при загрузке, и победа «маршрут вернулся на старт» — отклонено по той же причине плюс лишнее состояние: клетка старта меняет тип уже после загрузки.
- `solved` при `soilCount <= 1` (победа «вся земля, кроме клетки под кроликом») — отклонено: визуально остаётся незамощённая клетка, проверка приёмки «замостить весь soil» не выполняется.
- Победа = «нет доступных ходов» — отклонено: совпадает с предыдущим вариантом, но формулировка через тупик смешивает две разные вещи (победа и проигрыш).

**Следствия для правил (инварианты):**

- Клетка под игроком — `road` на всём протяжении партии, включая момент старта: игрок начинает на уже замощённой клетке (см. D7), поэтому исключений из правила нет.
- Стартовая клетка не является ресурсом: она не входит в `soilCount`, с неё можно уйти, но вернуться нельзя — ход на `road` запрещён тем же правилом, что и на любой другой замощённый асфальт.
- Стартовая клетка не является целью партии: условие победы — «не осталось ни одной `soil`», а не «вернуться на старт». Стартовый `road` — это точка входа, а не финишная черта.

### D2. Сборка одной командой `bun build`

**Что:** `bun build src/index.ts --target=browser --outdir=dist`, `index.html` подключает `./dist/index.js`. Для разработки — `bun build --watch` плюс любой статический сервер (`bunx serve .`).

**Почему:** `.ts` браузер не исполняет, нативная загрузка модулей возможна только с браузерными флагами (`--experimental-strip-types` и аналоги), что неприемлемо как основной путь. `bun build` уже доступен в выбранном инструментарии — ноль новых зависимостей, один выходной файл, работает в любом браузере.

**Альтернативы:**
- Dev-сервер на `Bun.serve`, отдающий `.ts` транспилированным — отклонено: опора на недокументированное поведение (в Bun 1.4 `static`-API уже отличается от описанного в старых версиях), плюс появляется расхождение между dev-путём и единственным «прод»-путём.
- `tsc --outDir` + нативный ESM — отклонено: при `moduleResolution: Bundler` импорты пишутся с расширением `.ts`, браузер их не разрешит, нужна перепись расширений; плюс десятки сетевых запросов в dev вместо одного файла.
- Отдельный раннер (`vite`, `esbuild`) — отклонено: противоречит «0 runtime, минимум зависимостей» и не нужно для тридцати модулей.

**Побочно:** `bunx serve` при первом запуске тянет пакет из сети; на это не завязываем приёмку — подойдёт любой статический сервер, все пути в `index.html` относительные.

### D3. Core — чистые функции, состояние мутируемое

**Что:** `GameState` — плоский объект (`grid`, `width`, `height`, `player`, `soilCount`, `solved`); `canMove` возвращает целевую клетку или `null`, `tryMove` мутирует состояние и возвращает `boolean`. Классов нет, копий состояния нет, клеточные координаты целочисленные.

**Почему:** состояние меняется по одному тайлу за ход, иммутабельные копии сетки дали бы O(n²) на ход без выигрыша. Мутируемый вариант тривиально тестируется (см. D10) и совпадает с `plan.md`.

**Альтернативы:** редьюсер с чистыми переходами и клонированием сетки — отклонено: больше кода, больше копий, никакой пользы на масштабе одного уровня.

### D4. Ввод: очередь направлений, а не один слот

**Что:** `src/input/*` только разбирают событие в `Dir` и кладут в очередь `Dir[]`, владеет которой `src/index.ts`; за один `update` вызывается `shift()` и применяется ровно один ход. Клавиатура: четыре стрелки, `event.repeat === true` игнорируется, для стрелок вызывается `preventDefault()`. Свайп: Pointer Events, порог 24 CSS-px по максимальной из осей, при превышении берётся доминирующая ось; смещение ниже порога и «тап без движения» не дают хода.

**Почему очередь, а не `pendingDir` из `plan.md`:** `player-input` требует, чтобы второе срабатывание между кадрами не потерялось, а было обработано позже. Одиночный слот второе срабатывание перезаписывает. Очередь — это `push`/`shift`, два вызова.

**Почему `preventDefault` для стрелок:** страница при прокрутке от стрелок уезжает; требование «страница не прокручивается» в спеках сформулировано для свайпа, но для стрелок нужно то же самое — это одна строка.

**Почему блокировка скролла через CSS, а не через `preventDefault` на touch:** `touch-action: none` на `canvas` и `overscroll-behavior: none` на `html, body` делают это декларативно и одинаково на всех браузерах; JS-обработчики `touchmove` не нужны.

**Альтернативы:** `KeyboardEvent.code` + отдельные слушатели на четыре клавиши — отклонено, один `keydown` с `switch` по `event.key` короче. Порог 16 px вместо 24 — отклонено: 24 меньше ловит случайные микросдвиги при тапе; точное значение подбирается на реальном устройстве (см. Open Questions).

### D5. Точечная перерисовка: событие вычисляется в `index.ts`

**Что:** `view/renderer.ts` владеет offscreen-слоем и экспортирует `renderAll()` и `redrawTile(x, y)`. `src/index.ts` сохраняет позицию игрока до `tryMove`; если ход удался, вызывает `redrawTile` для клетки, которая изменила тип. `core` о колбэках и о canvas не знает.

**Почему:** за ход меняется ровно одна клетка, поэтому событие «перерисовать» выводится из факта смены позиции — это две строки в `index.ts` и ноль изменений в core. Вариант с событийной шиной в `GameState` (`onCellPaved`) отклонён: ради одного события это лишняя связность между чистым ядром и рендерером. Вариант «каждый кадр сравнивать сетку с эталоном» отклонён: O(w·h) на кадр вместо O(1).

### D6. Canvas, devicePixelRatio и размер тайла

**Что:** backing store канваса = CSS-размер × `devicePixelRatio`, `ctx.setTransform(dpr, 0, 0, dpr, 0, 0)`, `imageSmoothingEnabled = false`. Размер тайла — `floor(min(cssW / gridW, cssH / gridH))`, минимум 1; сетка центрируется целочисленным смещением, чтобы не было дробных пикселей. Вся эта арифметика живёт в `view/layout.ts` как `computeLayout` (тестируется без canvas, см. D10), рендерер получает готовые числа. Слушатель `resize` пересчитывает размеры и вызывает `renderAll()` (offscreen-слой зависит от размера тайла). В CSS канваса — `image-rendering: pixelated` как страховка.

**Почему DPR-backing, а не только CSS-масштабирование:** `pixelated` даёт nearest-neighbour и без размытия, но при нецелом масштабе пиксели разного размера — сетка «гуляет». Собственный backing store на `dpr` даёт предсказуемую резкость и целочисленные размеры клеток. Требование «чёткость при `devicePixelRatio > 1`» закрывается обоими механизмами сразу.

**Альтернативы:** фиксированный маленький backing store (например, 320×240) и только CSS-растягивание — отклонено как основной путь: сценарий изменения размера окна из `game-rendering` тогда выполняется без всякой логики, но качество зависит от браузера; вариант с целочисленным масштабом (только 1×, 2×, 3×) отклонён: оставляет незанятое поле на экранах, где 1× мал, а 2× велик.

### D7. Валидация данных — вручную, без библиотек

**Что:** `src/data/levels-loader.ts` экспортирует `parseManifest` и `parseLevel(data: unknown): LevelData` — ручные проверки: `id` — непустая строка; `width`/`height` — положительные целые; `tiles.length === height`; длина каждой строки `=== width`; каждый элемент принадлежит `{'wall','soil','road'}`; `start` присутствует, в границах и указывает на `road`. При загрузке по записи манифеста сверяется совпадение идентификаторов. Ошибка — `throw new Error` с указанием причины; `index.ts` ловит её, показывает сообщение и не запускает цикл.

**Почему:** JSON-файлы — внешние данные, проверка на границе доверия обязательна (это прямое требование `level-loading`). Библиотека схем ради шести проверок — лишняя зависимость; `unknown` + ручные guards дают то же самое средствами языка.

**Альтернативы:** объявлять стартовую клетку как `soil` в данных и замощать её при загрузке — отклонено: одна и та же карта в данных означала бы разные вещи до и после загрузки, а ошибка в данных дала бы не «старт на земле», а непредсказуемый счётчик.

**Следствие для кода:** при `noUncheckedIndexedAccess` выражения `grid[y][x]` дают `CellType | undefined`, поэтому `core` вынужден сужать тип (проверка `if (!row) continue`, как в `plan.md`). Это осознанная цена строгого режима, а не обходной путь.

### D8. Атлас: `tileSize` берётся из кадра `wall`

**Что:** `view/sprite-atlas.ts` грузит `atlas.json`, затем изображение `meta.image` относительно JSON. Тайлы квадратные, поэтому размер тайла берётся как ширина кадра `wall` — единственный источник истины в атласе, никакого отдельного поля `meta.tileSize`. `getFrame(name)` бросает ошибку с именем запрошенного кадра, если его нет. Ошибка загрузки изображения — сообщение и отказ стартовать (как требует `game-rendering`).

**Альтернативы:** отдельное поле `meta.tileSize` в `atlas.json` — отклонено: дублирование значения, которое уже есть в кадре; рассинхрон — лишний класс ошибок. Масштабирование кадра до размера тайла, если они разойдутся — отклонено: скрывает ошибку данных вместо того, чтобы её показать.

### D9. Аниматор игрока — closure-фабрика, время в миллисекундах

**Что:** `createSpriteAnimator(frames, durations)` возвращает `{ advance(dtMs), current() }`. Внутренне — `elapsed` и индекс кадра; пока `elapsed >= duration[i]`, вычитается длительность и индекс берётся по модулю. Обновляется только в `update(dt)`, к ходам не привязан.

**Почему:** спека требует брать длительность каждого кадра из атласа (то есть длительности могут различаться), поэтому деление общего времени на одну константу не годится. Накопление остатка работает и при одинаковых длительностях, и при разных, и не требует предрассчёта кумулятивных сумм. Класс с полями не даёт ничего, кроме лишних строк.

### D10. Тесты — `bun test`, а DOM остаётся тонкой обвязкой

**Что:** `bun test`, скрипт `bun run test`, который входит в `bun run check` вместе с `typecheck` и `lint`. Единственная новая dev-зависимость — `@types/bun` (без неё `bun:test` не типизируется). Тесты лежат рядом с кодом: `src/core/game.test.ts`, `src/core/level-types.test.ts`, `src/data/levels-loader.test.ts`, `src/input/direction.test.ts`, `src/view/layout.test.ts`, `src/view/sprite-atlas.test.ts`.

**Что тестируется:** правила хода и инвариант «клетка под игроком всегда `road`»; отказ на `wall`, на `road`, за границей и на неизвестном направлении без изменения состояния; победа при `soilCount === 0`; победа без возврата на стартовую клетку; счётчик `soil` при загрузке; весь список отказов `parseLevel` из D7; доминирующая ось и порог свайпа, игнорирование `repeat` у стрелок; цикл аниматора с разными длительностями кадров; раскладка (размер тайла, целочисленное смещение, `devicePixelRatio`).

**Чем это тестируется:** вся содержательная логика — чистые функции, DOM в них не участвует. Привязка к событиям сводится к разбору аргумента, поэтому пороги и правила проверяются без синтетических событий:
- `src/input/direction.ts`: `decodeKey(key: string): Dir | null` и `decodeSwipe(dx: number, dy: number, threshold: number): Dir | null`; слушатели только передают `event.key` и разницу `clientX`/`clientY`.
- `src/view/layout.ts`: `computeLayout(cssW, cssH, gridW, gridH): Layout` (размер тайла, смещение сетки) и `playerRect(x, y, layout)`; рендерер получает готовые числа и ничего не считает сам.

Сам вызов Canvas 2D (`drawImage`, `setTransform`) юнит-тестами не проверяется: это тонкая обвязка, её проверяют глазами в браузере.

**Почему `bun test`:** раннер уже входит в инструментарий проекта и обязателен как пакетный менеджер, `describe`/`test`/`expect` идут из коробки, watch — флагом, конфиг не нужен. Ноль новых раннеров и ноль конфига при полноценных юнит-тестах.

**Почему `@types/bun` окупается:** игра визуальная, поэтому почти всё поведение живёт в логике, а не в разметке, и проверяться будет много: парсер, правила, ввод, раскладка. Один тип-пакет дешевле, чем десятки `any` в тестах или `// @ts-expect-error` перед каждым импортом.

**Альтернативы:**
- Один assert-скрипт `scripts/selfcheck.ts` (прошлый вариант) — отклонено: при десятках кейсов на правила и парсер это самописный раннер с худшими сообщениями об ошибках, чем у встроенного.
- `vitest` / `jest` — отклонено: новая ветка зависимостей, конфиг и DOM-окружение ради кода с нулём runtime-зависимостей.
- Снапшоты картинки (`getImageData` + эталонные буферы) — отклонено: атлас-заглушка одноцветный, такой тест проверял бы PNG-энкодер из D11, а не игру.

### D11. Плейсхолдерный атлас генерируется скриптом

**Что:** `public/assets/sprites/atlas.png` создаётся `scripts/gen-atlas.ts`: минимальный кодировщик PNG на `node:zlib` (строки с фильтром 0, CRC32) рисует одноцветные квадраты 16×16 по координатам из `atlas.json`. Скрипт остаётся в репозитории, чтобы заглушка была воспроизводима.

**Почему:** бинарный файл невозможно держать в git как «ещё одну строку», а нарисовать его без библиотеки иначе нельзя. Тридцать строк против непрозрачного блоба в diff.

**Альтернативы:** захардкоженный base64-блоб PNG — отклонено: нечитаемо и непроверяемо глазами, правка координат невозможна. Внешний редактор спрайтов в зависимости — отклонено: противоречит нулю зависимостей и нужно один раз.

### D12. Победа наблюдаема через `console`, без UI

**Что:** при первом переходе `solved` в `true` игра пишет одно сообщение в консоль; экран победы не делается.

**Почему:** UI вне scope, но критерий приёмки («замостить весь soil тестового уровня») должен быть проверяем. Одна строка `console.log` вместо оверлея.

## Risks / Trade-offs

- **[Правило разрешает запечатать себе тупик]** маршрут необратим, а проигрыша не показывают: игрок может остаться на `soil` без доступных ходов → принято для скелета (см. Non-Goals); признак тупика добавляется отдельным изменением вместе с любым текстом на экране.
- **[Правило «выиграл — вернись на старт» всплывёт в интерпретации]** стартовый `road` легко принять за финишную черту → зафиксировано в `game-rules` («стартовая клетка не является целью») и проверяется тестом: победа наступает без возврата на старт.
- **[Тестовый уровень обязан иметь выигрышный маршрут]** иначе приёмку не пройти → уровень делается плотным блоком `soil` в рамке из `wall` с `road`-стартом в углу, где маршрут «змейкой» очевиден; тот же маршрут прогоняется в `src/core/game.test.ts`.
- **[`bunx serve` требует сети при первом запуске]** → приёмка не зависит от него: подойдёт любой статический сервер, пути относительные, сборка в `dist/` самодостаточна.
- **[Offscreen-слой перерисовывается целиком на `resize`]** — на каждый вызов события, без коалесцинга → приемлемо: событие штучное, а полная перерисовка уровня это десятки `drawImage`.
- **[Плейсхолдерный атлас одноцветный]** — не проверяет визуальную разницу спрайтов и границы между типами клеток → конструкция атласа проверяется только тем, что имена кадров используются, а не координаты; реальный атлас приходит отдельным изменением.
- **[Валидация уровней дублирует типы]** (`unknown` → guards в `parseLevel` и тип `CellType`) → осознанный размен: рантайм-проверки нужны для внешних данных, а типы нужны для `core`. Совпадение набора значений фиксируется одним `const`-массивом в `core/level-types.ts`, а не двумя независимыми списками.

## Migration Plan

Применимость ограниченная: изменение первое, затрагиваемого кода в репозитории нет. Порядок внедрения:

1. Конфиги (`package.json` с dev-зависимостью `@types/bun`, `tsconfig.json`, `biome.json`) и `index.html` с подключением `./dist/index.js`.
2. Плейсхолдерные данные: `public/data/levels/{index.json,level-001.json}` (старт — `road` в углу) и `scripts/gen-atlas.ts` → `atlas.png` + `atlas.json`.
3. `src/core/*` (типы, состояние, правила, парсер уровня) вместе с тестами `src/core/*.test.ts` и `src/data/*.test.ts`.
4. `src/view/*` (включая `layout.ts`), `src/input/*`, `src/loop/*`, затем `src/index.ts` — сборка всех частей.
5. Проверка приёмки: `bun run check` (typecheck + lint + test), затем `bun run dev` и прохождение уровня стрелками и свайпом до сообщения о победе в консоли.

Откат: репозиторий пуст, откат — удаление добавленных файлов либо `git revert` первого коммита этого изменения. Миграции данных и обратной совместимости нет.
