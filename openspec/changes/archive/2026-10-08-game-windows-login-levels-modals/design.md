## Context

См. `proposal.md` (Why). Текущее состояние: `src/index.ts` в `bootstrap()` грузит атласы + манифест, берёт `manifest.levels[0]`, создаёт `GameState` и запускает `game-loop`; победа/тупик (`solved`/`stuck` из `src/core/game-rules.ts`) только логируются в консоль. Canvas занимает всё окно (`index.html`), рендер — `src/view/renderer.ts`. Ограничения: ассеты окон — цельные PNG (`ui/logo.png`, `ui/lvlsel/*`, `ui/modal/*`, `ui/button/*`), отдельных картинок кнопок для модалок нет; формат уровней и манифеста не меняем; ядро правил не меняем.

## Goals / Non-Goals

**Goals:**
- Законченный цикл entry → level-select → game → win/fail/menu на готовых PNG.
- Прогресс прохождения переживает перезагрузку (localStorage).
- Ввод в игру блокируется под открытым модальным окном; restart/next/back работают из каждой модалки.

**Non-Goals:**
- Анимации переходов между экранами, звук, сетевой бэкенд/авторизация.
- Изменение формата уровней, манифеста, `game-rules`, тайлового рендера и атласов.
- Редактор уровней, настройки, пауза по таймеру.

## Decisions

### 1. UI — DOM-оверлей поверх canvas, а не отрисовка в canvas
Окна и модалки — обычные DOM-элементы (`<div>` + `<img>` из `public/assets/ui/...`) поверх `<canvas id="game">`, клики — нативные DOM. Атласы остаются только для тайлов/кролика.
Альтернатива — рисовать окна в canvas и считать хит-зоны вручную: отклонено, больше кода (хит-тесты, ресайз, доступность), а PNG модалок уже содержат оформление целиком.

### 2. Один контроллер экранов: entry → level-select → game (+modal)
Состояния: `entry`, `levels`, `game`, модалка — флаг поверх `game` (`none | menu | win | fail`). `bootstrap()` показывает `entry`, уровень грузится только после выбора (лениво через существующий `loadLevel`). Переходы:
- `restart` = `createGameState(тот же LevelData)` + `renderAll` + сброс флага модалки;
- `next/skip` = `manifest.levels[i+1]` (по `id` текущего), на последнем уровне — fallback к `levels`;
- `back` = показать `levels` (игровой цикл останавливается или игнорирует очередь ввода).
Альтернатива — роутер/история URL: отклонено, YAGNI для трёх экранов.

### 3. Прогресс — один ключ localStorage
Ключ вида `oneway.done.v1`, значение — JSON-массив `id` пройденных уровней. Чтение при отрисовке списка (`done.png` vs `none.png`), запись при `solved`. `skip` не пишет. Весь доступ к storage в `try/catch` с in-memory fallback (приватный режим).
Альтернатива — отдельный ключ на уровень или IndexedDB: отклонено, один массив проще и хватает.

### 4. Кнопки модалок — процентные хит-зоны поверх цельной картинки
`win.png` (2 кнопки), `fail.png`/`menu.png` (по 3 кнопки) — кнопки это области внутри картинки, поэтому поверх `<img>` кладутся прозрачные `<button>` с относительным (`%`) позиционированием. Все координаты хит-зон — константами в одном месте рядом с UI-кодом.
Альтернатива — нарезать PNG на отдельные кнопки: отклонено, правим готовые ассеты и плодим файлы.

### 5. UI-ассеты живут в `public/assets/ui/`
`ui/*.png` подключаются как `<img src>` напрямую, без упаковки в спрайт-атлас и без `tools/`-конвейера (он только для тайлов/кролика).

## Risks / Trade-offs

- [Риск] Хит-зоны кнопок на модалках разъедутся на разных размерах экрана → проценты от размера картинки + ручная проверка на десктопе и мобильной ширине; константы зон в одном месте для быстрой калибровки.
- [Риск] `localStorage` недоступен (приватный режим, quota) → `try/catch` + in-memory fallback: прогресс живёт до перезагрузки, игра не падает.
- [Риск] PNG модалок/арта тяжёлые или грузятся с задержкой → стандартный прелоад `<img>` экранов при старте; окно `levels`/`game` ждёт `load` ключевых картинок.
- [Trade-off] DOM-поверх-canvas дублирует слой отрисовки, но это минимальный код против ручного хит-тестинга в canvas.
